## 0. What this brief is (and is not)

WI-13 landed the tariff-schedule surface; WI-13.1 landed the
per-statutory-lane records (`_registeredLanes`, `registerLane`,
`retireLane`, `resolveLane(s)`, `isLaneActive`). Both emit MIP-0002-style
`_actionLog` entries via the shared `emitAction` helper. What the log does
**not** carry today is a payload the consumer can *reconstruct and verify*:
per `V1.1-DESIGN.md §7.1`, every `RegistryActionEntry` carries only
`{ kind, scheduleId, nodeId, epoch, actionHash, emittedAt }`, and the
`actionHash` is a **non-invertible authorization commitment** (it binds
`selfBytes`, the domain tag, `currentEpoch`, `currentTime`, and the
op-specific params — *not* the canonical stored record body). WI-13.1's
own §7.1 therefore ruled the event stream out as a reconstruction source
and forced the keeper to re-scan map state.

WI-14 (EBT vNext) needs the opposite. `VNEXT-DESIGN.md §3.2` selected
**option (iii), registry-side event commitment**, as the mirror-freshness
mechanism: the keeper's mirror-write EBT circuit takes the registry event
body plus a proof-of-inclusion in the registry's action log, and verifies
it in-circuit against a `registryActionLogRoot`. "Freshness comes for
free: the event is the truth, the mirror-write moves the event into the
mirror map." That mechanism requires two things WI-13.1 does not expose:
a **canonical, recomputable payload hash** per in-scope event, and a
**committed root** over the action log. WI-13.2 adds exactly those.

**This brief IS:** the spec + Cursor dispatch to (a) widen
`RegistryActionEntry` with a canonical `payloadHash: Bytes<32>`, (b) add a
`registryActionLogRoot: Bytes<32>` ledger scalar updated on every
`emitAction`, and (c) add read circuits for keepers — as an **additive
amendment** to `tariff-registry/tariff-registry-v1.compact`.

**This brief is NOT:**
- A change to any WI-13.1 semantics. Every existing circuit body's
  *governance behaviour* is preserved bit-for-bit; the only additions are
  a new field written inside `emitAction` and a root update also inside
  `emitAction`. See §SCOPE for the exact touch-points and I-13.2-F.
- A new event kind. WI-13.2 widens the payload of five *existing* kinds.
- An in-circuit inclusion verifier. Proof *generation* is off-chain
  (keeper's job, spec'd here for compatibility); proof *verification*
  in-circuit is WI-14's job (`VNEXT-DESIGN.md §7.1`).
- A change to EBT, LD, multisig, or community-poll. DO NOT touch them.

## §SCOPE — what WI-13.2 DOES

### A. `RegistryActionEntry` payload widening

Add one field:

```
struct RegistryActionEntry {
  kind:        Uint<8>,
  scheduleId:  Bytes<32>,
  nodeId:      Bytes<32>,
  epoch:       Uint<64>,
  actionHash:  Bytes<32>,   // UNCHANGED — authorization commitment
  emittedAt:   Uint<64>,
  payloadHash: Bytes<32>,   // NEW — canonical mirror-payload commitment
}
```

`actionHash` keeps its exact current meaning and value (the federation /
operator authorization commitment). `payloadHash` is a **new, distinct**
commitment: `persistentHash` over the *canonical serialization of the
mirror-relevant event body* with a per-kind domain-separation tag. The
two hashes serve different consumers — `actionHash` gates the write,
`payloadHash` lets WI-14 reconstruct-and-verify the mirror. They are
never conflated.

For the five in-scope kinds — **0 `SCHEDULE_REGISTERED`, 1
`LANE_REGISTERED`, 2 `retuneClass`, 3 `SCHEDULE_RETIRED`, 7
`LANE_RETIRED`** — `payloadHash` is computed by a new helper
`actionPayloadHash(kind, …fields…)` per §B below. For any *other* kind
(4 `advanceEpoch`, 5 `setNationalContext`, 6 `setFederationAuthority`),
`payloadHash` is set to the reserved sentinel `pad(32, "")` (all-zero) —
those kinds are not mirrored and carry no reconstructable body. The
executing session MUST NOT invent payloads for the non-mirrored kinds.

> **Domain-tag correction (resolved in this brief; see §ESCALATION).**
> VNEXT-DESIGN §3.5 proposed the per-kind tag
> `pp:tariff:v1:actionpayload:{kindName}`. That literal string **does not
> fit** the `pad(32, …)` 32-byte budget the contract's hashing idiom
> requires (`pp:tariff:v1:` is 13 bytes; `actionpayload:` adds 14 → 27
> before any kind name; `…:registerLane` overflows to 39 bytes). WI-13.2
> therefore uses a **single fixed tag** `pp:tariff:v1:actionPayload`
> (26 bytes, fits) and binds the **kind byte as the first hashed field**.
> This yields identical per-kind domain separation (distinct `kind` ⇒
> distinct hash) while staying inside the idiom. This is a mechanical
> fit-to-budget adjustment, not a semantic change; see §DECISIONS.

### B. Precise payload schemas per kind (I-13.2-A canonicalization)

Every `payloadHash` is
`persistentHash<Vector<N, Bytes<32>>>([ tag, kindByte, …body… ])` where
`tag = pad(32, "pp:tariff:v1:actionPayload")` and
`kindByte = (kind as Field) as Bytes<32>`. Every scalar field is widened
to `Bytes<32>` via `(x as Field) as Bytes<32>` exactly as the existing
`actionHash` construction sites already do (e.g. L854–L860). **Canonical
order = the field-declaration order of the source struct.** This order is
locked *here*; WI-14 recomputes against it byte-for-byte (VNEXT-DESIGN
§7.1 `verifyEventProof` step 1). Any drift = broken mirror.

**Kind 1 `LANE_REGISTERED` — all 12 `LaneRecord` fields** (VNEXT-DESIGN
§3.5: "the payload MUST include the full `LaneRecord` fields the mirror
needs (all 12 of them)"). `N = 14` (tag + kindByte + 12):

```
persistentHash<Vector<14, Bytes<32>>>([
  pad(32, "pp:tariff:v1:actionPayload"),
  (1 as Field) as Bytes<32>,          // kind
  record.scheduleId,                  //  1
  (record.laneKindByte as Field) as Bytes<32>,   //  2
  record.leviedBy,                    //  3
  (record.bpsShare as Field) as Bytes<32>,       //  4
  record.remitAddress,                //  5
  (record.basis as Field) as Bytes<32>,          //  6
  record.applicabilityHash,           //  7
  record.statuteRefHash,              //  8
  (record.effectiveEpoch as Field) as Bytes<32>, //  9
  (record.retiredEpoch  as Field) as Bytes<32>,  // 10 (= 0 at registration)
  (record.remittanceMode as Field) as Bytes<32>, // 11
  (record.registeredAt as Field) as Bytes<32>,   // 12
])
```

The hash is computed over the **exact `LaneRecord` value inserted into
`_registeredLanes`** (built at L901–L914), so a keeper that reads the map
record reconstructs the identical hash. This is precisely what
`mirrorRegisterLane` asserts (`VNEXT-DESIGN §7.2`:
`recHash == entry.payloadHash`).

**Kind 7 `LANE_RETIRED` — the retired `LaneRecord`, same 12 fields, same
order, `N = 14`.** The body is the *retired* record (L972–L985), i.e.
identical to the live record except `retiredEpoch = _currentEpoch.read()`.
`mirrorRetireLane` overwrites the mirror entry with this retired version
(VNEXT-DESIGN §7.3), so committing the full retired record — not just a
"retire" flag — is required.

**Kind 0 `SCHEDULE_REGISTERED` — all 8 `ScheduleRecord` fields,
declaration order, `N = 10`:** `scheduleId, nodeId, scheduleHash,
operatorPubkey, effectiveEpoch, retiredEpoch (= 0), refRateFiatPerKwh,
registeredAt` (built L564–L573). WI-14's `mirrorScheduleLifecycle` needs
only `scheduleId` + liveness, but committing the full record is cheap and
future-proofs the class-total mirror (VNEXT-DESIGN §7.4/§7.5).

**Kind 3 `SCHEDULE_RETIRED` — the retired `ScheduleRecord`, same 8
fields, order, `N = 10`.** Body = the retired record (L617–L626),
`retiredEpoch = _currentEpoch.read()`.

**Kind 2 `retuneClass` — `scheduleId, classPath`, the 6 `SplitShares`
subfields (declaration order), `rateFiatPerKwh`, `lastUpdatedAt`;
`N = 12`:**

```
persistentHash<Vector<12, Bytes<32>>>([
  pad(32, "pp:tariff:v1:actionPayload"),
  (2 as Field) as Bytes<32>,          // kind
  scheduleId,                         //  1
  classPath,                          //  2
  (split.producerShareBps  as Field) as Bytes<32>,  // 3
  (split.ldShareBps        as Field) as Bytes<32>,  // 4
  (split.opsShareBps       as Field) as Bytes<32>,  // 5
  (split.daoShareBps       as Field) as Bytes<32>,  // 6
  (split.operatorMarginBps as Field) as Bytes<32>,  // 7
  (split.statutoryTotalBps as Field) as Bytes<32>,  // 8
  (rateFiatPerKwh as Field) as Bytes<32>,           // 9
  (lastUpdatedAt  as Field) as Bytes<32>,           // 10  (= currentTime)
])
```

WI-14's `mirrorClassStatutoryTotal` extracts `statutoryTotalBps` for the
`_classStatutoryTotalBpsMirror` write (VNEXT-DESIGN §7.5); committing the
full split lets WI-14 cross-check the whole-class sum backstop (I-14-K).

> **Note on `retuneClass`'s existing local `payloadHash` (L1059).**
> `retuneClass` already computes a local variable named `payloadHash` for
> the *operator signature* — that is the **authorization** hash and it
> flows into `emitAction`'s `actionHash` slot (L1143). Do NOT reuse it as
> the new `RegistryActionEntry.payloadHash`. Rename the local to
> `sigHash` (or `authHash`) to avoid confusion, and compute the new
> canonical `actionPayloadHash(2, …)` separately. This is the one place
> the naming genuinely collides; the rest of the contract calls the
> authorization hash `actionHash` already.

### C. `registryActionLogRoot: Bytes<32>` ledger field + on-chain update

Add:

```
export ledger registryActionLogRoot: Bytes<32>;
```

updated on **every** `emitAction` call (all kinds, including the
non-mirrored ones — the log is over the whole action stream; only the
*payload* is kind-selective). Commitment scheme: **append-only
incremental Merkle tree of fixed depth `D = CAL-13.2-D`**, leaf at
position `seq` = the entry's `payloadHash` (for non-mirrored kinds the
leaf is the `pad(32,"")` sentinel — still a well-defined leaf).

**Recommended scheme: Merkle tree (not hash-chain).** Rationale in
§DECISIONS; the short version: WI-14's `EventProof` (VNEXT-DESIGN §7.1) is
already Merkle-shaped — `merkleProof: Vector<D, Bytes<32>>`,
`merkleSiblings: Vector<D, Bool>`, and a `reconstructRoot(proof)` that
rebuilds a root from `(payloadHash, siblings, path)`. Only a fixed-depth
Merkle tree yields a **bounded, fixed-width** inclusion proof that
WI-14's in-circuit verifier can consume. A running hash-chain would force
WI-14 to carry an *unbounded* tail (all payloads between `seq` and head)
to prove inclusion, which no fixed `Vector<D>` witness can express.

On-chain update mechanics (append at index `seq = _actionSeq.read()`):
- Maintain a **frontier** ledger `Vector<D, Bytes<32>>` (the rightmost
  filled node at each level) plus the precomputed zero-subtree hashes.
- On append, fold the new leaf up `D` levels using the frontier and zero
  hashes, writing the updated frontier and the new root. This is a fixed
  `D`-iteration unroll — the **same idiom** already in the contract's
  `assertCharterMembership` 12-level unroll (L383–L419). Cost: `D`
  `persistentHash` calls per emit. Bounded, ZK-friendly, deterministic.
- Node/leaf domain tags (all ≤ 32 bytes, verified):
  - pair-node hash: `pad(32, "pp:tariff:v1:actionLogNode")`
  - empty-leaf constant: `pad(32, "pp:tariff:v1:actionLogEmpty")`
  - the root-commitment / genesis-anchor domain:
    `pad(32, "pp:tariff:v1:actionLogRoot")` (per VNEXT-DESIGN §3.5).
  - **Leaf = the raw `payloadHash`** (NOT re-hashed), because
    VNEXT-DESIGN §7.1 `reconstructRoot` starts its climb from
    `proof.payloadHash` directly. Position is bound by the path index
    (`merkleSiblings` bits = the big-endian bits of `seq`), not by a
    seq-in-leaf hash. Do not add a leaf-domain wrap around `payloadHash`
    or WI-14's reconstruction breaks.

The internal pair-hash MUST match what WI-14's `reconstructRoot` uses:
`persistentHash<Vector<3, Bytes<32>>>([nodeTag, left, right])`, left/right
ordered by the path bit exactly as `assertCharterMembership` does
(L384–L419). Lock that shape here; WI-14 mirrors it.

### D. Read circuits

- `export circuit getActionEntry(seq: Uint<64>): RegistryActionEntry` —
  assert `_actionLog.member(seq)` (`ACTION_LOG_SEQ_MISSING`), return the
  entry. Keepers fetch the authoritative event body (incl. `payloadHash`)
  from here.
- `export circuit getActionPayloadHash(seq: Uint<64>): Bytes<32>` —
  same membership assert, returns only `entry.payloadHash`. Provided as
  the cheap targeted read (VNEXT-DESIGN §3.5 "or a more targeted
  `getActionPayloadHash(seq)`"). Both are pure reads (I-F: no mutation,
  no value primitives, no events).

### E. `EventProof` shape compatibility

WI-14's `EventProof` witness (VNEXT-DESIGN §7.1) is:

```
struct EventProof {
  actionSeq:      Uint<64>,
  payloadHash:    Bytes<32>,
  merkleProof:    Vector<D, Bytes<32>>,
  merkleSiblings: Vector<D, Bool>,
}
```

WI-13.2's obligations toward this struct:
- Export a `payloadHash` per in-scope entry whose value equals what a
  keeper recomputes from the map record (§B). ✔ (field on
  `RegistryActionEntry`).
- Export a `registryActionLogRoot` such that `reconstructRoot(proof)`
  over `(payloadHash, merkleProof, merkleSiblings)` equals the root at
  the height the proof references. ✔ (§C, matching pair-hash shape).
- Commit to `D` — the tree depth — as **`CAL-13.2-D`**. `merkleProof` and
  `merkleSiblings` are `Vector<D>`. `D` is the depth-of-the-log ceiling.
- **WI-13.2 exposes proof *generation* off-chain** (keeper walks the tree
  it reconstructs from `getActionEntry`/`getActionPayloadHash` reads and
  produces `(merkleProof, merkleSiblings)`). WI-13.2 does **NOT**
  implement in-circuit inclusion verification — that is WI-14's
  `verifyEventProof` (VNEXT-DESIGN §7.1). The WI-13.2 test suite includes
  one *integration-preview* test (§REQUIRED TESTS T5) that runs the
  off-chain generator and simulates WI-14's in-circuit check to prove the
  shapes line up, but ships no verifier circuit.

### F. Backward compatibility + migration

WI-13.1's existing state MUST migrate cleanly. The constructor accepts
**either** fresh init **or** WI-13.1 migration:

- **Fresh init:** `registryActionLogRoot` = the empty-tree root
  `EMPTY_ROOT(D)` (the depth-`D` fold of `actionLogEmpty` leaves); the
  frontier is all-empty; the internal `_actionLogBaseSeq` checkpoint = 0.
- **WI-13.1 migration:** `registryActionLogRoot` is seeded to
  `EMPTY_ROOT(D)` as well, and `_actionLogBaseSeq` is set to the current
  `_actionSeq.read()` (the head at amendment time). From that seq forward,
  every `emitAction` appends a `payloadHash` leaf and extends the root.

**Recommended migration path: from-amendment-forward-only** (NOT
retroactive). Rationale in §DECISIONS; the decisive facts:
1. Historical `_actionLog` entries physically **cannot** yield a
   canonical `payloadHash`: they store only the non-invertible
   `actionHash` (V1.1-DESIGN §7.1), never the record body. Recomputing
   would require re-supplying every historical record off-chain — and is
   **impossible in principle** for lanes that were retired-then-
   re-registered, because `_registeredLanes` overwrites at the same key
   (I-13.1-F) and the superseded record is gone.
2. WI-14's mirror is bootstrapped at *its* constructor time from the
   post-WI-13.2 registry state (VNEXT-DESIGN §7.1: "the initial value is
   set at constructor time from TariffRegistry's post-WI-13.2 state").
   It never needs to prove inclusion of a pre-amendment event.
3. Forward-only keeps the amendment a strict superset: pre-amendment
   entries remain readable via `getActionEntry` with `payloadHash ==
   pad(32,"")` (the "pre-amendment, not mirror-verifiable" sentinel), and
   the committed root covers amendment-forward leaves only.

**Unchanged surfaces (I-13.2-F):** the federation-gated setter pattern,
`consumeFederationApproval`, `_federationAuthority`, charter membership
(`_governanceRoot`, `assertCharterMembership`), `_registeredLanes`,
`_classEntries`, `_registeredSchedules`, `_activeScheduleByNode`,
`_retuneNonces`, `_retuneLastTime`, and every read view
(`resolvePath`, `resolveLane(s)`, `isLaneActive`, …) are untouched in
behaviour. `SplitShares`, `LaneRecord`, `ScheduleRecord`, `ClassEntry`
struct shapes are untouched (§DO NOT).

## §INVARIANTS THAT MUST HOLD

Each maps to a mechanism in the amended `.compact` and a test in the
harness.

**I-13.2-A — payloadHash canonicalization.** For each in-scope kind,
`payloadHash` is computed over the exact serialization declared in
§SCOPE B (tag + kind byte + declaration-ordered fields, each widened
`(x as Field) as Bytes<32>`). The serialization is fixed by this brief;
no executing-session latitude on field order, tag, or widening idiom.

**I-13.2-B — payloadHash present on every in-scope emit.** Every
`emitAction` for kinds 0, 1, 2, 3, 7 writes a non-sentinel `payloadHash`
computed per I-13.2-A. Kinds 4, 5, 6 write the `pad(32,"")` sentinel.
No in-scope emit path may leave `payloadHash` unset or stale.

**I-13.2-C — actionLogRoot monotonic.** `registryActionLogRoot` only ever
advances by appending; it is never rewound, cleared, or recomputed from
scratch after init. `_actionSeq` is append-only (`Counter`), so the tree
only ever grows. There is no circuit that decrements the head or mutates
a filled leaf.

**I-13.2-D — actionLogRoot deterministic.** The same ordered sequence of
`(kind, payloadHash)` appends produces a **byte-identical**
`registryActionLogRoot`, independent of block time, caller, or witness
values beyond the committed fields. (Follows from persistentHash
determinism + fixed leaf/node tags + fixed depth.)

**I-13.2-E — payloadHash uniquely determines mirror state.** No two
distinct mirror-relevant states hash to the same `payloadHash`: the kind
byte + all state-bearing fields are inside the hash in a fixed order, so
there is no ambiguous `LaneRecord` (or `ScheduleRecord` / class split)
that collides (modulo persistentHash collision resistance). In
particular a live vs. retired `LaneRecord` differ in `retiredEpoch` and
therefore in `payloadHash`; a kind-1 and kind-7 body over the same record
differ in the kind byte.

**I-13.2-F — WI-13.1 semantic preservation.** Every WI-13 and WI-13.1
test passes **unchanged**. No governance behaviour, error label, event
kind, or read result changes for any pre-existing circuit. The amendment
is observationally invisible except for the new `payloadHash` field, the
new root ledger, and the two new read circuits.

## §ERROR LABELS (normative, alphabetical)

New labels are deliberately minimal — the amendment is observational and
its writes happen inside already-gated paths.

| Label                     | Guards                | Where fired                                                     |
|---------------------------|-----------------------|----------------------------------------------------------------|
