## 1) Motivation

On the 2026-07-19 Preview deploy attempt, the deployment flow reached
`Transaction.feesWithMargin` and failed with:

> `Error: exceeded block limit in transaction fee computation`

Attribution:

- WI-13.3 dispatch brief (`WI-13.3-DISPATCH-BRIEF.md`)
- Deploy path status from `feat/wi14-tariff-registry-preview-deploy`
  commit `6746e19`
- Error class is consistent with Midnight node/docs variants
  `FeeCalculation.BlockLimitExceeded` / `BlockLimitExceededError`

Root cause (from WI-13.2 constructor body):

- constructor currently performs action-log empty-tree bootstrap inline
- loop shape is `for (const i of 0..24)` (24 iterations in Compact's half-open range)
- per iteration:
  - `_actionLogZeros.insert(i, z)`
  - `_actionLogFrontier.insert(i, z)`
  - `_actionLogClimb = persistentHash([nodeTag, z, z])`
- net constructor hot path:
  - 48 map inserts
  - 24 persistentHash calls for the climb
  - 24 writes to `_actionLogClimb`
  - plus non-loop init writes and final `_initialized = true`

Why this amendment exists:

- WI-14 mirror-daemon rollout depends on a Preview-live TariffRegistry
- current deploy tx cannot pass block limits with constructor-loop inline
- the loop is semantically valid but transaction-shape-invalid in deploy context
- we need to preserve WI-13.2 semantics while moving heavy bootstrap post-deploy

Non-goals:

- do not change `ACTION_LOG_DEPTH` (=24)
- do not alter WI-13.1/WI-13.2 runtime branch semantics
- do not modify mirror-daemon code in this branch
- do not perform Preview deploy from this session

## 2) CAL-13.2-D block-budget analysis

### 2.1 Evidence available

Hard evidence:

1. Existing deploy attempt failed at fee/block-limit computation before submission.
2. Failure point is deterministic for this constructor shape.
3. Action-log append path (`appendActionLogLeaf`) already exists as runtime path and
   was accepted as viable in WI-13.2 design/test posture.

Source references:

- constructor loop in `tariff-registry-v1.compact`
- append path in `appendActionLogLeaf` (`tariff-registry-v1.compact`)
- Midnight docs: block limits are multi-dimensional synthetic cost:
  `readTime`, `computeTime`, `blockUsage`, `bytesWritten`, `bytesChurned`
- Midnight docs do not publish a stable, reviewer-usable per-op coefficient table
  in the checked-in repo context for exact closed-form tx cost by map insert/hash.

### 2.2 Why exact closed-form coefficients are not asserted here

The branch/repo snapshot does not contain:

- vendored ledger-v8 cost-model source constants
- local `@midnight/*` package sources exposing block-limit coefficients
- a deterministic on-repo utility already wired to print per-tx synthetic cost
  components for candidate calls

Therefore, this analysis uses:

- exact operation counts from contract code
- a comparative envelope against an existing runtime path (`appendActionLogLeaf`)
- conservative sharding margins

### 2.3 Operation-count comparison (deterministic)

Definitions:

- D = 24 levels (Compact half-open loop `0..24` -> indices 0..23)
- Constructor loop work per level:
  - 2 map inserts (`zeros`, `frontier`)
  - 1 hash (`persistentHash`)
  - 1 write to climb accumulator (`_actionLogClimb`)

Legacy constructor full bootstrap (D=24):

- map inserts: 24 * 2 = 48
- hashes: 24
- climb writes: 24
- plus final root/baseSeq/initialized writes

Runtime append path worst case per emit:

- map inserts: up to 24 (`frontier.insert` on left-path bits)
- hashes: 24
- climb writes: 24
- plus root write

Relative weight intuition:

- constructor bootstrap has exactly 2x the guaranteed map-insert count of a
  single append path (48 vs <=24), with same hash count
- this makes constructor bootstrap materially heavier on write-dimensions
  (`bytesWritten`, `bytesChurned`) than a single append path

### 2.4 Option-A feasibility test via analysis

Option A is one-shot post-deploy bootstrap with the full 24-level loop.

What is known:

- deploy+constructor-loop fails

What is unknown:

- whether loop-only call in one tx fits under Preview block limits

Why unknown remains material:

- no per-op coefficients here to prove one-shot headroom
- constructor failure alone cannot prove loop-only success or failure

Conclusion:

- Option A cannot be defended with high confidence from available data
  in this branch context
- choosing A would shift risk from deploy-time to bootstrap-call time
  without guaranteed resolution

### 2.5 Sharded envelope calculation (Option B candidate)

Choose shard width K levels per call (except final shard).

Per shard operation counts:

- map inserts: `2 * K`
- hashes: `K`
- climb writes: `K`

Candidate K values:

- K=12 -> 24 inserts, 12 hashes
- K=8  -> 16 inserts, 8 hashes
- K=6  -> 12 inserts, 6 hashes

Conservative choice:

- K=8 as default keeper target
- rationale:
  - inserts (16) are well below append-path potential insert envelope (<=24)
  - hashes (8) are one-third of full bootstrap and one-third of append-path hash count
  - leaves substantial margin for fixed call overhead and non-loop assertions

Largest single-shard size considered confidently safe in this doc:

- **K=8 levels per call**

Resulting call count to reach D=24:

- 3 calls: `0->8`, `8->16`, `16->24`

This is an operational recommendation, not a hard protocol cap:

- circuit allows any monotonic shardEnd progression up to 24
- keeper may tune shard size downward if network conditions tighten

### 2.6 Block-budget number recorded

Recorded budget number for WI-13.3 handoff:

- **Conservative shard budget: 8 levels/call**
- equivalent loop work per call:
  - 16 map inserts
  - 8 persistent hashes
  - 8 climb updates

This is the explicit number used by this amendment's design choice.

## 3) Refactor shape chosen (A / B / C)

### 3.1 Decision

Chosen option: **B (sharded bootstrap)**.

### 3.2 Rationale

1. Deploy failure is confirmed and blocking.
2. One-shot loop-only fit is not provable from available local evidence.
3. Option B guarantees progress under unknown/tight block envelopes by allowing
   smaller pre-init calls.
4. Option B preserves all WI-13.2 runtime semantics after initialization:
   same zeros/frontier/root construction, same baseSeq boundary, same initialized gate.
5. Option B avoids introducing a broader init-surface migration of all constructor
   fields into a new `initialize()` flow (Option C), minimizing moving parts.

### 3.3 Why A was not selected

- A may still fail if full 24-level bootstrap exceeds limits by itself.
- This branch cannot analytically prove A-safe with concrete coefficients.
- B removes that uncertainty.

### 3.4 Why C was not selected

- C is a known pattern in other contracts, but it would migrate all constructor
  initialization into a new lifecycle surface.
- For WI-13.3's narrow objective (de-risk heavy loop), C is larger-scope than needed.
- B keeps constructor ownership/constants setup unchanged and moves only
  load-bearing heavy tree bootstrap to post-deploy shards.

### 3.5 Sealed-init preservation

`_initialized` stays sealed and still receives exactly one write:

- constructor writes `_initialized = true` exactly once (constructor-ran marker)
- bootstrap writes `_bootstrapComplete = true` at terminal shard
- `assertInitialized()` now enforces BOTH `_initialized` and `_bootstrapComplete`
- all existing branch/read call sites stay unchanged and inherit the tighter gate

This matches LD v2.2.1's proven two-flag shape: sealed constructor marker plus
runtime readiness flag.

### 3.6 Sealed-field compile contradiction resolution

The first kenya retry compile (run via `setsid` fallback because kenya lacks
`nohup`) failed with the Compact rule:

> exported circuits cannot modify sealed ledger fields

That surfaced a contradiction in the original WI-13.3 draft: keeping
`_initialized` sealed while moving its terminal write into an exported
post-deploy bootstrap circuit is invalid in Compact. The resolved shape keeps
`_initialized` sealed and constructor-only, and introduces
`_bootstrapComplete` as the exported-circuit completion flag. This is
cross-checked against LivingDividend v2.2.1's initialization pattern.

## 7) Option-B `_actionLogClimb` shard persistence invariant

`_actionLogClimb` is already exported ledger state and persists across calls.
Option B depends on this persistence.

Invariant statement:

- On shard entry, loop continuation must start from persisted `_actionLogClimb`,
  not from a fresh local seed, except initial constructor seed.

Implementation shape used:

1. Constructor seeds:
   - `_actionLogClimb = pad(32, "pp:tariff:v1:actionLogEmpty")`
   - `_actionLogBootstrapCursor = 0`
2. Each bootstrap shard:
   - processes levels in half-open range `[cursor, shardEnd)`
   - writes zeros/frontier at each processed level
   - updates `_actionLogClimb` each processed level
   - sets cursor = shardEnd
3. Terminal shard (`shardEnd == 24`):
   - commits `registryActionLogRoot = _actionLogClimb`
   - commits `_actionLogBaseSeq = _actionSeq.read()`
   - writes `_bootstrapComplete = true`

Consequence:

- shard decomposition is observationally equivalent to one contiguous
  24-level loop over the same hash transition relation.

## Appendix A - Semantic equivalence sketch (legacy loop vs shards)

Let:

- `z0 = pad(32, "pp:tariff:v1:actionLogEmpty")`
- `H(x) = persistentHash([nodeTag, x, x])`
- `zi+1 = H(zi)`

Legacy constructor computes:

- for i in [0,24):
  - `zeros[i] = zi`
  - `frontier[i] = zi`
  - `climb = zi+1`
- final root = `z24`

Sharded bootstrap computes same recurrence over partitioned ranges
whose concatenation equals [0,24):

- shard 1: [0,a)
- shard 2: [a,b)
- ...
- shard n: [y,24)

Because each step depends only on prior `climb` and persisted `climb`
is carried between shards, final `climb` after shard n is exactly `z24`.

Therefore final root parity is preserved.
