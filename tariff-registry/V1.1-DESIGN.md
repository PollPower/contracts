## 2. Source-level specification

### 2.0 Compile-time constants

```
// MAX_STATUTORY_LANES: maximum number of statutory lanes per schedule.
// Sized at 10 to accommodate multi-authority statutory environments
// (e.g. Kenya: KRA VAT + EPRA levy + REP levy + WARMA levy + county cess
// + Petroleum Development Levy + Railway Development Levy + …).
// Referenced by:
//   - _registeredLaneCount ledger map (per-schedule cap)
//   - registerLane count-cap enforcement (checked-cast on (MAX - count))
//   - resolveLanes Vector width
const MAX_STATUTORY_LANES: Uint<8> = 10 as Uint<8>;
```

Cursor implements this either as a `pure circuit` returning `Uint<8>`
or as a plain compile-time literal — whichever form compactc 0.30.0
accepts cleanly. Whichever idiom is chosen, the name
`MAX_STATUTORY_LANES` MUST be used consistently in every reference
(ledger declaration comment, registerLane enforcement, resolveLanes
vector width, tests).

### 2.1 `LaneRecord` struct (declared alongside `ScheduleRecord`)

Field order below is canonical for the record's byte layout and for
every hash that folds a `LaneRecord` in — Cursor MUST NOT reorder.

```
struct LaneRecord {
  scheduleId:        Bytes<32>,
  laneKindByte:      Uint<8>,
  leviedBy:          Bytes<32>,
  bpsShare:          Uint<16>,
  remitAddress:      Bytes<32>,
  basis:             Uint<8>,
  applicabilityHash: Bytes<32>,
  statuteRefHash:    Bytes<32>,
  effectiveEpoch:    Uint<64>,
  retiredEpoch:      Uint<64>,       // 0 = live
  remittanceMode:    Uint<8>,        // CAL-11
  registeredAt:      Uint<64>,
}
```

Field notes:

- `scheduleId` — the parent schedule's id. MUST resolve to a live
  entry in `_registeredSchedules` at register-lane time
  (`SCHEDULE_NOT_FOUND` / `SCHEDULE_NOT_LIVE`). Set from the caller's
  `scheduleId` param, `disclose()`-wrapped.
- `laneKindByte` — enum 0=VAT, 1=levy, 2=cess, 3=duty per
  STATUTORY-LANES-MODEL §2. Circuit enforces `laneKindByte < 16`
  in `registerLane` via bare checked-cast (I-13.1-J); the 0..15 range
  is reserved for statute-defined lane kinds, higher values are
  disallowed to keep the space bounded for future off-chain
  interpretation (WI-17 renderer).
- `leviedBy` — canonical authority id ("KRA", "EPRA", county-id, ...).
  Circuit treats it as opaque `Bytes<32>`. STATUTORY-LANES-MODEL B-4
  scope-to-nationRef is enforced off-chain by the statute-to-lane
  ceremony (STATUTORY-LANES-MODEL §7 R-3), not in-circuit.
- `bpsShare` — statute-set. NOT enforced-consistent with
  `SplitShares.statutoryTotalBps` in-circuit: an operator's aggregate
  is the ceiling that WI-13's `retuneClass` step 7 already checks;
  per-lane consistency with that aggregate is off-chain policy per
  STATUTORY-LANES-MODEL §7 change-ceremony rules. WI-13.1 stores the
  bps, WI-14 reads it, statutory correctness lives in the ceremony.
- `remitAddress` — where WI-14's settle circuit routes this lane's
  share. Opaque `Bytes<32>`; either a fiat-door marker or an on-chain
  address per `remittanceMode`.
- `basis` — enum matching STATUTORY-LANES-MODEL §2
  (0=pre-tax energy charge, 1=full retail price, ...). Opaque byte
  in-circuit.
- `applicabilityHash` — commitment to the off-chain per-class
  applicability rule (FULL / REDUCED / EXEMPT per class). Circuit
  stores the hash; rule text and per-class disposition live off-chain
  (STATUTORY-LANES-MODEL §5).
- `statuteRefHash` — commitment to the enabling-law citation. The
  R-3 change-ceremony publishes the full citation; the hash pins it
  on-chain.
- `effectiveEpoch` — MUST be strictly greater than
  `_currentEpoch.read()` at register-lane time (I-13.1-D via checked
  cast). Never retroactive.
- `retiredEpoch` — 0 while active; set to `_currentEpoch.read()` at
  retire-lane time. Retirement is one-way per record; a retired lane's
  key MAY be re-registered with a fresh record superseding
  (I-13.1-E).
- `remittanceMode` — CAL-11: 0=fiat-door, 1=on-chain per
  STATUTORY-LANES-MODEL §3. Circuit accepts any `Uint<8>` value;
  interpretation lives in WI-14's settle branch.
- `registeredAt` — block time from the `currentTime` argument
  (`blockTimeGte(currentTime)`-validated as in every V1 branch op).

### 2.2 New ledger declarations

Placed immediately after `_activeScheduleByNode` in the ledger section
(mirrors the schedule-map placement pattern from V1's `_registeredSchedules`
/ `_activeScheduleByNode` block):

```
// nodeId → active scheduleId (unchanged, existing).
// scheduleId + classPathHash → current ClassEntry (unchanged, existing).
// _registeredLanes: (scheduleId, leviedBy, laneKindByte) composite key
// → LaneRecord. Keeper-observable via _actionLog kind ∈
// {1 LANE_REGISTERED, 7 LANE_RETIRED}. WI-14's settle circuit calls
// resolveLanes to route statutory shares in-circuit.
export ledger _registeredLanes: Map<Bytes<32>, LaneRecord>;

// _registeredLaneCount: per-schedule live lane count. Keyed by
// scheduleId. Value: count of currently-registered lanes on this
// schedule. Retired lanes STILL COUNT against the slot budget —
// retire+reregister at a different (leviedBy, kind) still consumes a
// slot; matches STATUTORY-LANES-MODEL §7 discipline. Incremented on
// registerLane only when the key is fresh (not present in
// _registeredLanes); NEVER decremented. Bounded by MAX_STATUTORY_LANES.
export ledger _registeredLaneCount: Map<Bytes<32>, Uint<8>>;
```

No new sets. No new sealed constants.

### 2.3 `laneKey` helper

Placed alongside V1's composite-key helpers (the same section as
`classSplitKey`, if present, or after the `retuneNonce`-derivation
helper). Domain tag `pp:tariff:v1:laneKey` reserved here.

```
// Composite key for a statutory lane record:
// (scheduleId, leviedBy, laneKindByte). The leviedBy component makes
// multi-authority same-kind lanes representable (e.g. KRA-VAT and
// county-VAT as two distinct lanes on the same schedule) — which is
// the whole point of HIGH-1's fix.
circuit laneKey(
  scheduleId:   Bytes<32>,
  leviedBy:     Bytes<32>,
  laneKindByte: Uint<8>,
): Bytes<32> {
  const kindBytes = (disclose(laneKindByte) as Field) as Bytes<32>;
  return persistentHash<Vector<4, Bytes<32>>>([
    pad(32, "pp:tariff:v1:laneKey"),
    disclose(scheduleId),
    disclose(leviedBy),
    kindBytes,
  ]);
}
```

Determinism: two callers passing the same
`(scheduleId, leviedBy, laneKindByte)` triple must produce
byte-identical keys. `Uint<8>` → `Field` → `Bytes<32>` mirrors V1's
`effectiveEpochBytes = (disclose(effectiveEpoch) as Field) as Bytes<32>`
pattern.

Every call site of `laneKey` in §2.4 (registerLane), §2.5 (retireLane),
§2.6 (resolveLane), §2.7 (resolveLanes), §2.8 (isLaneActive) passes
`leviedBy` in the new position.

### 2.4 `registerLane` circuit

Skeleton follows V1's `registerSchedule`, extended for lane-specific
enforcement:
`assertInitialized` → `blockTimeGte` → schedule exists + live →
charter proof → epoch non-retroactive (checked cast) → kind < 16
(checked cast, I-13.1-J) → per-schedule count ≤ MAX_STATUTORY_LANES
(checked cast, I-13.1-I) → action-hash construction →
`consumeFederationApproval` → duplicate-key check → insert →
count-increment (if fresh key) → `emitAction`.

**Full parameter list (verbatim):**

```
export circuit registerLane(
  scheduleId:        Bytes<32>,
  laneKindByte:      Uint<8>,
  leviedBy:          Bytes<32>,
  bpsShare:          Uint<16>,
  remitAddress:      Bytes<32>,
  basis:             Uint<8>,
  applicabilityHash: Bytes<32>,
  statuteRefHash:    Bytes<32>,
  effectiveEpoch:    Uint<64>,
  remittanceMode:    Uint<8>,
  charterProof:      CharterProof,
  currentTime:       Uint<64>,
): []
```

**No operator signature parameter.** The lane is federation-gated
only — the federation IS the authority that translated the statute
into a `rateBps` via the R-3 change ceremony (STATUTORY-LANES-MODEL
§7). No operator key path.

**Action-hash payload composition** (this is the critical detail
Cursor must get exactly right — it determines off-chain
bundle-builder compatibility for the msfed 3-of-5 seat approval
signing). Vector length 14, field order:

```
persistentHash<Vector<14, Bytes<32>>>([
  pad(32, "pp:tariff:v1:registerLane"),   // domain
  selfBytes(),                             // contract self-binding (M-2)
  disclose(scheduleId),
  kindBytes,                               // laneKindByte as Field as Bytes<32>
  disclose(leviedBy),
  bpsShareBytes,                           // bpsShare as Field as Bytes<32>
  disclose(remitAddress),
  basisBytes,                              // basis as Field as Bytes<32>
  disclose(applicabilityHash),
  disclose(statuteRefHash),
  effectiveEpochBytes,                     // effectiveEpoch as Field as Bytes<32>
  remittanceModeBytes,                     // remittanceMode as Field as Bytes<32>
  currentEpochBytes,                       // _currentEpoch.read() as Field as Bytes<32>
  timeBytes,                               // currentTime as Field as Bytes<32>
])
```

**Error labels** (all REVERTs, per V1-DESIGN.md §8 "MUST fail means
REVERT, not warning event"):

- `SCHEDULE_NOT_FOUND` — schedule id not in `_registeredSchedules`.
- `SCHEDULE_NOT_LIVE` — schedule exists but `retiredEpoch != 0`.
- `SCHEDULE_UNCHARTERED_NODE` — from `assertCharterMembership` on the
  schedule's `rec.nodeId` (mirrors V1's registerSchedule step 3).
- `FEDERATION_APPROVAL_INVALID` — from `consumeFederationApproval`.
- `FEDERATION_APPROVAL_REPLAYED` — from `consumeFederationApproval`.
- `LANE_ALREADY_REGISTERED` — duplicate check per I-13.1-E.

**Unlabeled reverts** (bare checked-cast underflow — no assert label,
same idiom as I-13.1-D epoch check in V1 convention):

- **Epoch non-retroactivity** — `(effectiveEpoch - currentEpoch - 1) as
  Uint<64>` underflows if `effectiveEpoch <= currentEpoch`.
- **Kind-range** (I-13.1-J) — `(16 - laneKindByte - 1) as Uint<8>`
  underflows if `laneKindByte >= 16`.
- **Count-cap** (I-13.1-I) — `(MAX_STATUTORY_LANES - priorCount - 1) as
  Uint<8>` underflows if `priorCount >= MAX_STATUTORY_LANES`.

Note: count-cap and kind-range violations revert with compiler-generic
underflow, same as I-13.1-D epoch check. This matches V1 convention;
labeled asserts are reserved for higher-level semantic errors.

**Full-body sketch** (top-to-bottom, mirrors registerSchedule L459+
byte-for-byte in shape):

```
export circuit registerLane(
  scheduleId:        Bytes<32>,
  laneKindByte:      Uint<8>,
  leviedBy:          Bytes<32>,
  bpsShare:          Uint<16>,
  remitAddress:      Bytes<32>,
  basis:             Uint<8>,
  applicabilityHash: Bytes<32>,
  statuteRefHash:    Bytes<32>,
  effectiveEpoch:    Uint<64>,
  remittanceMode:    Uint<8>,
  charterProof:      CharterProof,
  currentTime:       Uint<64>,
): [] {
  assertInitialized();
  assert(disclose(blockTimeGte(disclose(currentTime))),
         "registerLane: timestamp cannot be in the future");

  // (a) Schedule must exist and be live.
  const dSchedId = disclose(scheduleId);
  assert(_registeredSchedules.member(dSchedId), "SCHEDULE_NOT_FOUND");
  const schedRec = _registeredSchedules.lookup(dSchedId);
  assert(schedRec.retiredEpoch == 0 as Uint<64>, "SCHEDULE_NOT_LIVE");

  // (b) Charter proof binds the lane to the SCHEDULE'S nodeId.
  //     Same shape as registerSchedule step 3.
  assertCharterMembership(schedRec.nodeId, charterProof);

  // (c) I-13.1-D: effective epoch strictly in the future.
  //     Checked-cast underflow reverts if effectiveEpoch <= currentEpoch.
  const _epochGap = ((disclose(effectiveEpoch)
                      - _currentEpoch.read()
                      - 1) as Uint<64>);
  // Bare checked-cast IS the assertion (V1 §5.4 idiom); reverts with the
  // compiler-generic underflow message. No labeled assert.

  // (c') I-13.1-J: laneKindByte < 16 (reserved statute-kind range).
  //     Checked-cast underflow reverts if laneKindByte >= 16.
  const _kindInRange = ((16 as Uint<8>
                         - disclose(laneKindByte)
                         - 1 as Uint<8>) as Uint<8>);
  // Same bare-checked-cast pattern; no labeled error.

  // (c'') I-13.1-I: per-schedule lane count cap.
  //     priorCount is the current count for this schedule; underflow
  //     reverts if priorCount >= MAX_STATUTORY_LANES. (dSchedId already
  //     declared in step (a).)
  const priorCount = _registeredLaneCount.member(dSchedId)
    ? _registeredLaneCount.lookup(dSchedId) : 0 as Uint<8>;
  const _slotAvailable = ((MAX_STATUTORY_LANES
                           - priorCount
                           - 1 as Uint<8>) as Uint<8>);
  // Same bare-checked-cast pattern; no labeled error.

  // (d) Prepare the 14 hash inputs.
  const kindBytes         = (disclose(laneKindByte) as Field) as Bytes<32>;
  const bpsShareBytes     = (disclose(bpsShare) as Field) as Bytes<32>;
  const basisBytes        = (disclose(basis) as Field) as Bytes<32>;
  const effectiveEpochBytes = (disclose(effectiveEpoch) as Field) as Bytes<32>;
  const remittanceModeBytes = (disclose(remittanceMode) as Field) as Bytes<32>;
  const currentEpochBytes = (_currentEpoch.read() as Field) as Bytes<32>;
  const timeBytes         = (disclose(currentTime) as Field) as Bytes<32>;

  const actionHash = persistentHash<Vector<14, Bytes<32>>>([
    pad(32, "pp:tariff:v1:registerLane"),
    selfBytes(),
    dSchedId,
    kindBytes,
    disclose(leviedBy),
    bpsShareBytes,
    disclose(remitAddress),
    basisBytes,
    disclose(applicabilityHash),
    disclose(statuteRefHash),
    effectiveEpochBytes,
    remittanceModeBytes,
    currentEpochBytes,
    timeBytes,
  ]);

  // (e) I-13.1-A: federation approval + replay guard.
  consumeFederationApproval(
    actionHash,
    pad(32, "pp:tariff:v1:registerLane"),
  );

  // (f) I-13.1-E: duplicate check. Allow re-registration only if the
  //     existing key's record is retired (retiredEpoch != 0).
  //     Key derivation uses the NEW (scheduleId, leviedBy, laneKindByte)
  //     tuple — multi-authority same-kind lanes at different leviedBy
  //     get distinct keys and coexist.
  const key = laneKey(scheduleId, leviedBy, laneKindByte);
  const dKey = disclose(key);
  const keyPresent = _registeredLanes.member(dKey);
  assert(
    !keyPresent
      || _registeredLanes.lookup(dKey).retiredEpoch != 0 as Uint<64>,
    "LANE_ALREADY_REGISTERED"
  );

  // (g) Insert the LaneRecord (retiredEpoch = 0 = live).
  const record = LaneRecord {
    scheduleId:        dSchedId,
    laneKindByte:      disclose(laneKindByte),
    leviedBy:          disclose(leviedBy),
    bpsShare:          disclose(bpsShare),
    remitAddress:      disclose(remitAddress),
    basis:             disclose(basis),
    applicabilityHash: disclose(applicabilityHash),
    statuteRefHash:    disclose(statuteRefHash),
    effectiveEpoch:    disclose(effectiveEpoch),
    retiredEpoch:      0 as Uint<64>,
    remittanceMode:    disclose(remittanceMode),
    registeredAt:      disclose(currentTime),
  };
  _registeredLanes.insert(dKey, disclose(record));

  // (i') I-13.1-I: increment _registeredLaneCount ONLY when the key is
  //      fresh (not already present in _registeredLanes). Overwriting a
  //      retired record at the same key does NOT increment — the slot
  //      was already claimed. Retire+register at a DIFFERENT
  //      (leviedBy, kind) DOES increment. Checked cast belt-and-braces
  //      against future MAX bump underflow.
  if (!keyPresent) {
    _registeredLaneCount.insert(
      dSchedId,
      ((priorCount + 1 as Uint<8>) as Uint<8>),
    );
  }

  // (h) Emit action kind 1 = LANE_REGISTERED.
  emitAction(
    1 as Uint<8>,
    scheduleId,
    schedRec.nodeId,
    actionHash,
    currentTime,
  );
}
```

Note on step (f): using `||` short-circuits on the `.member` check; if
the compiler rejects that shape (some Compact idioms require ternary),
Cursor MAY rewrite as:

```
if (_registeredLanes.member(dKey)) {
  assert(
    _registeredLanes.lookup(dKey).retiredEpoch != 0 as Uint<64>,
    "LANE_ALREADY_REGISTERED"
  );
}
```

Both shapes preserve the semantic (I-13.1-E) contract.

### 2.5 `retireLane` circuit

Follows V1's `retireSchedule` skeleton, extended with `leviedBy` to
match the new `(scheduleId, leviedBy, laneKindByte)` key.

**Parameter list:**

```
export circuit retireLane(
  scheduleId:   Bytes<32>,
  leviedBy:     Bytes<32>,
  laneKindByte: Uint<8>,
  currentTime:  Uint<64>,
): []
```

**Action-hash payload** — vector length 7 (was 6; `leviedBy` slotted
after `scheduleId` to match register-side ordering):

```
persistentHash<Vector<7, Bytes<32>>>([
  pad(32, "pp:tariff:v1:retireLane"),
  selfBytes(),
  disclose(scheduleId),
  disclose(leviedBy),
  kindBytes,                     // laneKindByte as Field as Bytes<32>
  currentEpochBytes,
  timeBytes,
])
```

Count is NOT decremented on retire — the slot is preserved for audit
continuity per I-13.1-I. See §7 for the retire-slot-preservation
rationale.

**Error labels:**
- `LANE_NOT_FOUND` — key absent from `_registeredLanes`.
- `LANE_ALREADY_RETIRED` — record present but `retiredEpoch != 0`.
- `FEDERATION_APPROVAL_INVALID` — from `consumeFederationApproval`.
- `FEDERATION_APPROVAL_REPLAYED` — from `consumeFederationApproval`.

**Full-body sketch:**

```
export circuit retireLane(
  scheduleId:   Bytes<32>,
  leviedBy:     Bytes<32>,
  laneKindByte: Uint<8>,
  currentTime:  Uint<64>,
): [] {
  assertInitialized();
  assert(disclose(blockTimeGte(disclose(currentTime))),
         "retireLane: timestamp cannot be in the future");

  // (a) Look up the lane by (scheduleId, leviedBy, laneKindByte).
  const key = laneKey(scheduleId, leviedBy, laneKindByte);
  const dKey = disclose(key);
  assert(_registeredLanes.member(dKey), "LANE_NOT_FOUND");
  const rec = _registeredLanes.lookup(dKey);

  // (b) I-13.1-F: must be active.
  assert(rec.retiredEpoch == 0 as Uint<64>, "LANE_ALREADY_RETIRED");

  // (c) Prepare hash inputs.
  const kindBytes         = (disclose(laneKindByte) as Field) as Bytes<32>;
  const currentEpochBytes = (_currentEpoch.read() as Field) as Bytes<32>;
  const timeBytes         = (disclose(currentTime) as Field) as Bytes<32>;

  const actionHash = persistentHash<Vector<7, Bytes<32>>>([
    pad(32, "pp:tariff:v1:retireLane"),
    selfBytes(),
    disclose(scheduleId),
    disclose(leviedBy),
    kindBytes,
    currentEpochBytes,
    timeBytes,
  ]);

  // (d) Federation approval + replay guard.
  consumeFederationApproval(
    actionHash,
    pad(32, "pp:tariff:v1:retireLane"),
  );

  // (e) Mark retired; re-insert.
  const retired = LaneRecord {
    scheduleId:        rec.scheduleId,
    laneKindByte:      rec.laneKindByte,
    leviedBy:          rec.leviedBy,
    bpsShare:          rec.bpsShare,
    remitAddress:      rec.remitAddress,
    basis:             rec.basis,
    applicabilityHash: rec.applicabilityHash,
    statuteRefHash:    rec.statuteRefHash,
    effectiveEpoch:    rec.effectiveEpoch,
    retiredEpoch:      _currentEpoch.read(),
    remittanceMode:    rec.remittanceMode,
    registeredAt:      rec.registeredAt,
  };
  _registeredLanes.insert(dKey, disclose(retired));

  // (f) Emit action kind 7 = LANE_RETIRED.
  //     nodeId: look it up from the parent schedule for keeper-mirror parity.
  const schedRec = _registeredSchedules.lookup(disclose(scheduleId));
  emitAction(
    7 as Uint<8>,
    scheduleId,
    schedRec.nodeId,
    actionHash,
    currentTime,
  );
}
```

Note: `retireLane` does NOT re-check charter membership. The lane was
already charter-gated at register-time; retirement is a federation-only
act that undoes a federation-only insert. This mirrors `retireSchedule`'s
shape.

### 2.7 `resolveLanes` circuit — bounded batch

Cursor MAY prefer a helper-circuit if the ternary shape triggers
Compact idiom quirks (e.g. the `Maybe` pattern); the design admits
either implementation as long as the semantic contract holds:
zero-`LaneRecord` on missing key is the "no lane at this kind"
signal WI-14 branches on.

**Zero-record sentinel discriminator.** The unambiguous discriminator
for "real record vs zero record" is `rec.scheduleId != Bytes<32>::zero()`.
A real registered record's `scheduleId` cannot be all-zero (schedules
are registered under 32-byte ids derived from federation-approved
registration bundles — zero is not a reachable schedule id). Do NOT
use `bpsShare`, `laneKindByte`, `remitAddress`, or `basis` as
discriminator — those can legitimately be zero on a real record
(kind=0 is VAT, bpsShare=0 could be a placeholder, etc.).

**No `resolveLanesActive` variant.** The "populated + live" predicate
is specified in §7 and applied by WI-14 in-circuit; keeping
`resolveLanes` a pure read surface avoids duplicating epoch-gate
logic here.

### 2.8 `isLaneActive` circuit

```
export circuit isLaneActive(
  scheduleId:   Bytes<32>,
  leviedBy:     Bytes<32>,
  laneKindByte: Uint<8>,
): Boolean {
  assertInitialized();
  const key = laneKey(scheduleId, leviedBy, laneKindByte);
  if (!_registeredLanes.member(disclose(key))) {
    return false;
  }
  const rec = _registeredLanes.lookup(disclose(key));
  if (rec.retiredEpoch != 0 as Uint<64>) {
    return false;
  }
  return _currentEpoch.read() >= rec.effectiveEpoch;
}
```

Note: the final `>=` on `Uint<64>` is a numeric comparison, not on
`Field`, so it is allowed. If the compiler rejects it, rewrite as a
checked-cast helper Boolean.

## 7. Handoff to WI-14 (settle circuit consumer)

WI-14's settle circuit reads lane records from this registry via
`resolveLanes(scheduleId, leviedBys, laneKindBytes)`. The request-vector
sourcing pattern is:

1. **WI-14's OFF-CHAIN KEEPER reads `_registeredLanes` map state
   directly** (not the `_actionLog` event stream — see §7.1 below).
   For each schedule about to be settled, the keeper enumerates the
   schedule's live lanes from the map, filters for
   `effectiveEpoch <= currentEpoch` and `retiredEpoch == 0`, and
   builds:
     - `leviedBys:     Vector<10, Bytes<32>>` — padded with
       zero-address for empty slots
     - `laneKindBytes: Vector<10, Uint<8>>` — padded with 0 for empty
       slots
   The keeper deduplicates `(leviedBy, laneKindByte)` pairs before
   building the vectors (see §7.2).

2. Keeper passes these two vectors as **PUBLIC INPUTS** to WI-14's
   settle circuit.

3. WI-14's settle circuit calls
   `resolveLanes(scheduleId, leviedBys, laneKindBytes)` and receives
   `Vector<10, LaneRecord>`.

4. WI-14 applies the **"populated + live" predicate** per slot:
   ```
   rec.scheduleId != Bytes<32>::zero()             // discriminator: real record
   && rec.retiredEpoch == 0                        // not retired
   && _currentEpoch.read() >= rec.effectiveEpoch   // in-effect
   ```
   Only slots passing this predicate participate in routing.

5. WI-14 routes each populated lane's statutory share to
   `rec.remitAddress` per its `remittanceMode` field (0=fiat-door,
   1=on-chain per CAL-11).

No contract-to-contract call is required — WI-13.1 writes to
`_registeredLanes`, WI-14 reads via `resolveLanes`, and the two
contracts remain independently deployable.

Update the WI-14 dispatch brief
(`dispatch-briefs/WI-14-EBT-vNext.md`) to reference this section
before that session opens.

### 7.1 Why the keeper reads the map directly, not the event log

`_actionLog` entries for `LANE_REGISTERED` (kind=1) and `LANE_RETIRED`
(kind=7) carry only `{ scheduleId, nodeId, actionHash, epoch,
currentTime }`. They do NOT carry the `LaneRecord` fields
(`laneKindByte`, `leviedBy`, `remitAddress`, `bpsShare`, `basis`,
etc.) — the `actionHash` is a commitment to all the fields but is
non-invertible. Therefore the event stream cannot be the source of
truth for lane state reconstruction.

Events serve as **cache-invalidation signals only**: when the keeper
sees a `LANE_REGISTERED` or `LANE_RETIRED` event for a `scheduleId`,
it re-scans that schedule's lane set from `_registeredLanes` map
state. `emitAction` on the contract side is NOT modified — the change
is in the off-chain indexer's consumption discipline.

### 7.2 Deduplication rule

Supplying the same `(leviedBys[i], laneKindBytes[i])` pair twice in a
`resolveLanes` call returns the same `LaneRecord` twice (both slots
hit the same map key and get the same record). WI-14 MUST deduplicate
at the keeper level before passing the vectors in, or a naive sum
across slots will double-count remittances. `resolveLanes` itself is
a pure read — it does not enforce uniqueness across its request
vector; that's WI-14's responsibility.

### 7.3 Zero-record sentinel

An empty slot (either `leviedBys[i]` is zero-address, or the
`(leviedBys[i], laneKindBytes[i])` pair is not found in
`_registeredLanes`) returns a `LaneRecord` with all fields zero. The
unambiguous discriminator for "real record vs zero record" is:
```
rec.scheduleId != Bytes<32>::zero()
```
A real registered record's `scheduleId` is always a non-zero
federation-approved schedule id. Do NOT use `bpsShare`,
`laneKindByte`, `remitAddress`, or `basis` as discriminator — those
can legitimately be zero on a real record (kind=0 is VAT, an
informational lane could have `bpsShare=0`, etc.).
