# V1.1 Deferred Features

This file tracks tariff-registry V2 features that are **intentionally deferred**
to a future v1.1 deploy to keep the T+0 pilot Lane sibling under Midnight
Preview's per-extrinsic block-weight limit.

**Status:** ACTIVE deviation from `V2-SPLIT-DESIGN.md` for the pilot deploy.
All deferred features SHOULD be un-fenced and re-verified before v1.1 mainnet.

## Motivation

Empirical measurements on Midnight Preview (2026-07-29):

- `system.blockLength.max.normal` = 786,432 bytes (block-level cap)
- `system.blockWeights.perClass.normal.maxExtrinsic.refTime` = 1,299,891,843,000 (per-extrinsic weight cap)
- Successful `Schedule` deploy consumed **93.56%** of `maxExtrinsic.refTime`
- Failed `Lane` deploy attempts at 693 KB (attempt #4) and 580 KB (attempt #5)
  both rejected with `1010: Invalid Transaction: Transaction would exhaust
  the block limits`

Per-circuit deploy cost scales with **circuit count + circuit complexity**,
not raw `contract/index.js` bytes. Lane's 9 circuits (post PR #65 shrink)
exceeded the 6.4% headroom Schedule left in the maxExtrinsic budget.

Aggressive shrink strategy: fence all Lane exports except `registerLane`
(the sole day-1 required write path). This is a **weight optimization**
disguised as a code shrink — the goal is reducing on-chain circuit count.

## What is deferred

All fenced items are in `tariff-lane.compact` and delimited by
`// BEGIN DEFERRED-TO-V1.1-<region>` and `// END DEFERRED-TO-V1.1-<region>`
markers.

### Region F1: `_mirroredFederationAuthority` constructor init

Single line in the Lane constructor that seals the mirror authority at
genesis. Fenced because F3/F4 remove all readers of `_mirroredFederationAuthority`.

### Region F2: Lane read-view circuits

- `resolveLane(scheduleId, leviedBy, laneKindByte) -> LaneRecord`
- `resolveLanes(scheduleId, leviedBys, laneKindBytes) -> Vector<4, LaneRecord>`
- `isLaneActive(scheduleId, leviedBy, laneKindByte) -> Boolean`

**Zero production callers.** Verified 2026-07-29 across:
- `settlement-api` (main, post-PR #7 merge)
- `pollpower-v2-api`, `pollpower-ops-dashboard`
- `consumer-standalone`, `producer-standalone`
- `pollpower-app`, `pollpower-mobile`, `pollpower-central`

Only test callers exist in `tests/wi15.1/registry.test.mjs`,
`tests/wi15.1/lib.mjs`, and `tests/wi15.1/action-log.test.mjs`.

**Runtime workaround:** downstream code (e.g., `settlement-api/src/mirror-daemon/registry-reader.ts`)
reads `_registeredLanes` directly via the ledger accessor rather than through
a circuit call. This is the pattern that stays working.

### Region F3: `_mirrored*` ledger declarations

11 exported ledger cells:

- `_mirroredGovernanceRoot`, `_mirroredEpoch`
- `_mirroredLDFloorBps`, `_mirroredOpsFloorBps`, `_mirroredSanityBandPct`
- `_mirroredRefRateFiatPerKwh`
- `_mirroredFederationAuthority`
- `_mirroredSchedulesRoot`, `_mirroredSchedulesEpoch`
- `_mirroredAuditRoot`, `_mirroredAuditGlobalSeq`

No external reader (verified 2026-07-29 across the same repo set). Only
mirror circuits (F4, also fenced) read them.

### Region F4: Lane mirror-write circuits

- `mirrorGovernanceRoot(newRoot, epochAtMirror, govAuthoritySig, govAuthorityHash, currentTime)`
- `mirrorEpochAndFloors(newEpoch, newLDFloorBps, newOpsFloorBps, newSanityBandPct, ...)`
- `mirrorFederationAuthority(newAuthority, epochAtMirror, ...)`
- `mirrorSchedulesRoot(newRoot, epochAtMirror, ...)`
- `mirrorAuditRoot(newRoot, epochAtMirror, ...)`

**No production callers.** No mirror-writer daemon exists yet for
tariff-registry (per `memory/2026-07-18.md`: "Remaining deploy blocker:
mirror-write daemon does not exist yet"). The daemon brief at
`workspace/scratch/MIRROR-DAEMON-BRIEF.md` targets EBT v8, not
tariff-registry.

## Spec deviation acknowledgment

`V2-SPLIT-DESIGN.md` describes:
- §4.1-4.9: mirror-write endpoints per sibling
- §8.4 (I-15-B): monotone mirror-epoch invariant
- Mirror-based consistency model across all 5 siblings

**This deployment does NOT implement the mirror-consistency model on the
Lane sibling.** Other siblings (Governance, Schedule, Views) retain their
respective mirror circuits.

Lane in the pilot is a "write-only-through-registerLane" endpoint. Query
paths use ledger-direct reads on `_registeredLanes` from
`settlement-api/src/mirror-daemon/registry-reader.ts`.

## Un-fence for v1.1

Mechanical process, no state migration required for the mirror cells:

1. In `tariff-lane.compact`, for each region (F1, F2, F3, F4):
   - Strip leading `// ` from each line between the `BEGIN` and `END`
     markers.
   - Remove the fence header block and the BEGIN/END markers themselves.

2. Un-fence test files:
   - `tests/wi15.1/mirror-writes.test.mjs`
   - `tests/wi15.1/mirror-writes-genesis.test.mjs`
   - `tests/wi15.1/mirror-lib.mjs`
   - Any updates to `tests/wi15.1/registry.test.mjs`, `lib.mjs`,
     `action-log.test.mjs` that fenced test cases calling the read views.

3. Recompile Lane and verify circuit count matches original spec.

4. Deploy fresh Lane contract instance (pilot Lane is one-shot; no
   migration needed since `_mirrored*` cells only get written by newly-restored
   mirror circuits + the mirror daemon).

5. Delete this file.

## Reversal path (if aggressive shrink turns out to be wrong)

If future analysis shows Lane really does need the read views or mirrors
for a day-1 pilot flow we haven't identified, the un-fence process above
recovers full functionality. Cost: one Compact recompile (~6 min on kenya)
+ one fresh deploy attempt. No on-chain state is stranded because the fence
is applied BEFORE the pilot deploy.
